# ATCParserKit 1.4.0 — one transcript cleanup, shared by the parser and the screen

A speech recognizer does not hand you the words a controller said. It hands you `take-off`
where the phraseology says `takeoff`, `juliet` where ICAO says `juliett`, an `[unk]` token
where it gave up, and a callsign spelled out letter by letter. Every app on top of this
package was fixing those quirks itself — which meant each app fixed a slightly different set,
and the string shown on screen was not the string the parser matched.

1.4.0 moves that cleanup into the core as **`TranscriptCleaner`**, wires it into the
recognition path, and exposes it to every wrapper. Additive: nothing in 1.x, 1.2.0 or 1.3.0
changed.

---

## What is included

### `TranscriptCleaner` — the same fixups everywhere

```swift
TranscriptCleaner.clean("Descend three thousand")     // "Descend tree thousand"
TranscriptCleaner.displayText("x-ray alpha juliet")   // "XAJ"
```

Two entry points, because the two consumers want different things:

- **`clean`** feeds the parser and **preserves case** — the matcher lowercases internally, so
  uppercasing here would only destroy the original casing that readbacks speak from.
- **`displayText`** is `clean` plus uppercasing, for a text field.

The rules are whole-word, case-insensitive, applied in order: hyphen folding
(`take-off` → `takeoff`, `ads-b` → `adsb`, `low-altitude` → `low altitude`), ICAO spellings
(`juliet` → `juliett`, `alpha` → `alfa`, `three` → `tree`), and removals (`[unk]`, stray
commas). The word boundary is added only where the rule's own edge is a word character —
a `\b[unk]\b` would never fire, because `[` is not a word character, which is exactly why an
earlier version of these rules silently did nothing.

`TranscriptNormalizer` now runs `clean` as step 0, so **the recognition path and the display
share one cleanup**. That is the point of the release: `threefold` must not become `treefold`
on screen *or* in the matcher, and it cannot drift between them.

### A phonetically-spelled callsign folds to its code

```swift
TranscriptCleaner.clean("echo tango delta 615 descend")   // "ETD 615 descend"
```

A controller spelling a callsign gives the recognizer three ordinary English words, and
`ETD615` never matches them. Folding a **leading** run of two or more phonetic words into a
letter code makes it match, and makes it display as the code the pilot expects.

Two deliberate limits:

- **Leading only** — that is the callsign position. A phonetic word mid-command is a fix name
  or a runway designator, and the parser's own slot handling already resolves it in context.
- **Two or more words** — a lone `delta` or `victor` is an airline name or a plain English
  word. `delta 615` stays `DELTA 615`.

### Readbacks read numbers the ICAO way

`spokenDigits` now renders `3`, `4`, `5`, `9` as **tree, fower, fife, niner**. The digits a
controller actually reads aloud — headings, levels, squawks, callsigns — are read this way,
and it keeps what the library speaks consistent with what `TranscriptCleaner` expects to hear
back.

New `NumberWords.spokenFragment` renders an arbitrary fragment for speech, digit runs included:

```swift
NumberWords.spokenFragment("emirates 22 5")   // "emirates two two fife"
NumberWords.spokenFragment("aca125")          // "aca one two fife"
```

This exists for the "say again" case — echoing a fragment nothing matched. Handed straight to
a synthesiser, `22` becomes "twenty two", which is not a thing anyone says on frequency.
`NumberWords` is now `public` for the same reason.

### `displayText` crosses every boundary

The cleanup is only worth having if the text field uses it, and the text field is in
TypeScript or C#. So it is a wrapper API, not just a Swift one:

**C ABI** — a seventh exported symbol:

```c
char *atc_display_text(const char *transcript);   // free with atc_parser_free
```

**React Native:**

```ts
import { displayText } from '@ishant89/atc-parser-kit';
setTranscript(await displayText(rawFromRecognizer));
```

**Unity:**

```csharp
transcriptLabel.text = Parser.DisplayText(rawFromRecognizer);
```

Same string-in/string-out shape as `parse`, so it needs no handle and no lifetime.

### Fixed

- **A comma is a clause boundary, and the cleanup was eating it.** The stray-comma rule ran
  inside `clean`, which the normalizer calls before it looks for punctuation — so
  `"air india 123 report passing PJ, speedbird 45 report passing RE01"` lost its split and two
  aircraft collapsed into one readback. Commas are now dropped in `displayText` only. The
  screen still has no stray commas; the matcher still sees where one clause ended.

  Worth naming rather than quietly fixing: it is the predictable failure mode of putting a
  shared step in front of a pipeline that was already reading the raw text.

### Tests

**177**, up from 170. The new ones pin the cleanup rules (case preservation, whole-word
matching, `[unk]` and comma removal, empty input), the fold's two limits (leading-only, ≥2
words, a lone phonetic word left alone), ICAO fragment digits, and the comma regression above
against the wire test that caught it.

CI now verifies **seven** exported C symbols in both xcframework slices.

## What is still not included

- **Android, desktop, WebGL.** Unchanged: the wrappers bridge a compiled Swift binary.
- **A configurable rule table.** The replacement list is compiled in. Payload-supplied
  recognizer fixups would be the natural next step, since payloads already carry corrections.

---

## Upgrading

**From 1.3.0:** additive; nothing to do. Two things worth adopting:

1. **Show `displayText`, not the raw transcript.** Otherwise the screen and the matcher
   disagree, which is the confusion this release exists to remove.
2. **Expect ICAO digits in spoken output.** Any test that asserted "three" now reads "tree".
