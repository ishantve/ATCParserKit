# ATCParserKit 1.2.0 — template-driven recognition

**Additive. Nothing in 1.x changed.** `ATCParser().parse(_:)` / `parseToJSON(_:)`, the
`ParserResult` / `ParsedCommand` wire models, and the JSON contract are byte-for-byte what
they were in 1.1.1, so every existing caller — Swift, React Native, Unity — keeps working
without a line of change. That is why this is a minor version and not a 2.0.

What is new is a second, larger way to use the kit: instead of recognising a fixed set of
commands the library was compiled with, you hand it **your own phraseology payload** and it
recognises whatever that payload defines.

---

## Why this exists

1.x knew eleven commands, and it knew them because they were written into its source. Every
new instruction meant editing the library, and the vocabulary — spellings, digit words,
phonetics — was duplicated in each place that needed it.

Real ATC phraseology is a table someone else maintains: hundreds of templates across dozens
of categories, each with an ICAO wording, a readback, and a flag for whether it is available
yet. It changes without the app shipping. So the wording had to become **input**, not code.

1.2.0 is that change. You supply the templates; the kit does the matching, the value
extraction, and the readback.

---

## What is included

### Templates as input

```swift
let templates = try TemplateSet(data: payloadJSON)
let recognizer = CommandRecognizer(templates: templates)
let result = recognizer.recognize("air india 123 climb and maintain FL260, increase speed to 300 knots")
```

- **`TemplateSet(data:)`** — decodes a phraseology payload into templates grouped by
  category. `templates(in:)`, `template(id:)`, `enabled`, `disabled`, `categories`.
- **`CommandTemplate`** — one instruction: its pattern, its readback, its category, its
  backend code, and `isEnabled` (a template can be defined but not yet available).
- **`TemplatePattern`** — compiles `"[CALLSIGN] RADAR CLIMB TO FLIGHT LEVEL [LEVEL]"` into
  literals and slots. It keeps **two** forms: lowercased tokens for matching, and the
  original casing and punctuation for speech, because the text a controller hears and the
  text a matcher compares are not the same string.

### Payloads ship broken, and the kit says so

- **`TemplateSet.diagnostics`** — every problem found while decoding, rather than a silent
  best-effort: a readback naming a placeholder its instruction never supplies, an entry with
  no code, two templates whose literal words are identical so no matcher could tell them
  apart. These are the list you send back to whoever maintains the payload; they surface
  nowhere else.
- **`TemplateSet.Correction`** + **`applying(_:)`** — lets a deployment fix a known-bad
  entry at load time without forking the payload or the library. Each correction is meant to
  be deleted once the source is fixed, and the diagnostic keeps reporting the problem until
  it is.

### Matching

**`TemplateMatcher`** aligns a transcript against every template's literal words and scores
the fit. Defaults, all overridable:

| | |
|---|---|
| `minimumScore` | `0.5` |
| `minimumCoverage` | `0.6` |
| `maximumLiteralGap` | `2` |
| `optionalLiterals` | `["radar", "the"]` |

- **Multiple commands in one transmission.** Matches are selected non-overlapping and in
  spoken order, so *"climb and maintain FL260, increase speed to 300 knots, turn right
  heading 250"* yields three commands, not one.
- **Multiple aircraft in one transmission.** Each command carries its own callsign, carried
  forward from the last one spoken; `groupedByCallsign()` splits them.
- **Bounded callsign runs.** A callsign is 1–3 non-vocabulary words plus a flight number,
  and it must sit next to the instruction it belongs to — so an unrecognised word cannot be
  swallowed into a callsign that grows without limit.
- **`tiedWith`** reports templates that matched equally well, rather than picking one and
  hiding the ambiguity.

### Values

- **`SlotKind`** — 15 kinds (callsign, flightLevel, altitudeFeet, heading, speedKnots,
  degrees, runway, squawk, pressure, distance, time, frequency, fix, freeText, integer),
  each with its own valid range and digit width.
- **Parse width and spoken width are separate.** A flight level parses from two or three
  digits but is *spoken* as three — FL090 is "zero nine zero", not "nine zero". Squawk
  2000 is read digit by digit, not as two thousand.
- **`SlotRegistry`** resolves a placeholder name to a kind **in context**: a bare `[NUMBER]`
  is a runway when the words around it say runway and a speed when they say knots.
- **Homophone recovery.** Fixed-width slots get a second pass that repairs "for" → 4,
  "to"/"too" → 2, "won" → 1 — but only inside a slot that needs a digit there, never
  globally, because "turn to the left" must stay "to".

### Number words, both directions

- **`NumberWords`** — "two six zero" → 260, "seventy" → 70 → spoken back as "seven zero".
  Speech transcripts arrive as words, inconsistently: sometimes "FL two six zero",
  sometimes "FL 260", sometimes "FL 2 6 0". All three parse to the same value.
- **`Lexicon`** — spellings, abbreviations (`fl` → `flight level`), the two contractions
  that are genuinely safe (`take off` → `takeoff`, `stand by` → `standby`), and ICAO
  phonetics.

### Readbacks

- **`Readback`** splits a template's reply into its branches: the immediate readback, a
  **`Later:`** part the pilot owes when a condition is met, and an **`If not:`** /
  **`If incorrect:`** alternative for confirmation requests where the honest answer is
  "negative".
- **`ReadbackRenderer`** fills slots and renders each branch as speech.
- **`ReadbackComposer`** joins several readbacks for one aircraft into one utterance, so
  three instructions to the same aircraft get one reply, not three.
- **`unresolvedSlots`** names anything a branch still needs, so a caller cannot accidentally
  speak a sentence with a hole in it.

### Results

**`RecognizedCommand`** carries `callsign`, `category`, `code`, `backendCode`, `slots`,
`isEnabled`, `readback`, `matchedText`, `tiedWith`, `score`, `coverage`, and:

**`outcome`** — `.ok`, `.disabled`, or `.invalidValue`. A recognised-but-unavailable command
is *not* an error and *not* a success: it parsed, it gets its own reply, and it must not
execute. Collapsing that into a boolean is what makes a simulator quietly do the wrong
thing, so it is three cases.

**`RecognitionResult`** adds `unrecognized` — the parts of the transcript nothing matched.
Silence about them would be the bug.

### Tests

**151**, up from 13. They cover the matcher's selection and scoring, slot parsing and
rendering in both directions, the number lexicon, payload decoding and its diagnostics, and
readback composition including the deferred and alternative branches.

## What is *not* included

**The template API is Swift-only in 1.2.0.** The React Native and Unity wrappers still
expose 1.x `parse` / `parseToJSON` and nothing more.

This is a deliberate omission, not an oversight. The 1.x call is a pure string-to-string
function, which is why a C ABI and a JS bridge suit it. Template recognition needs a payload
loaded once and reused across many calls — a handle, with a lifetime — so the bridge becomes
create / recognise / release rather than one function. That is its own design and its own
tests, and shipping it half-done would be worse than saying it is next.

Also unchanged: the wrappers remain **iOS-only**. The Swift core runs anywhere Swift runs.

## Upgrading from 1.1.1

Nothing to do. Add nothing, change nothing — 1.x continues to work.

To adopt the template path, supply a payload:

```swift
// Load your phraseology once, keep the recognizer.
let templates = try TemplateSet(data: try Data(contentsOf: payloadURL))
    .applying(corrections)          // optional: known-bad entries
let recognizer = CommandRecognizer(templates: templates)

for diagnostic in templates.diagnostics {
    print("payload issue:", diagnostic)   // send these upstream
}

let result = recognizer.recognize(transcript)
for (callsign, spoken) in result.composedReadbacks() {
    speak(spoken)                   // one reply per aircraft
}
for command in result.commands where command.isActionable {
    apply(command)                  // .disabled / .invalidValue must not reach here
}
```

Two things worth getting right at the call site, because both were live bugs while this was
being built:

1. **Do not execute a command whose `outcome` is not `.ok`.** Check `isActionable`.
2. **Speak the branch you mean.** A confirmation has an `If not:` reply and a report has a
   `Later:` reply; rendering only the primary one means the aircraft answers "affirm" to a
   question whose truthful answer is "negative", which is worse than not answering.
