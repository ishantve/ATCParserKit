# ATCParserKit 1.3.0 — the template API on React Native and Unity

1.2.0 added template-driven recognition to the Swift core and left the wrappers behind. This
release finishes the job: **`Recognizer` is now available from TypeScript and C# as well as
Swift**, over one shared implementation. Nothing in 1.x or 1.2.0 changed, so this is again a
minor version.

That gap should not have shipped as a documented caveat. A version number is a promise, and
1.2.0's npm and UPM packages were stamped `1.2.0` while exposing the 1.1.1 API — which is why
those channels were never published at 1.2.0, and why 1.3.0 is the first version where every
platform means the same thing.

---

## What is included

### A handle-based bridge

`parse` is one function because parsing built-in commands is one pure string-to-string call.
Recognition is not: the phraseology payload is decoded once and reused for every transmission,
so it has a lifetime. Re-decoding per utterance would be wasteful and would throw away the
diagnostics, which only exist at decode time.

So the boundary became **create / use / release**, in all three bindings.

**C ABI** (`ATCParserFFI`) — four new symbols beside the existing two:

```c
void *atc_recognizer_create(const char *templates_json, char **error_json);
char *atc_recognizer_recognize(void *handle, const char *transcript);
char *atc_recognizer_diagnostics(void *handle);
void  atc_recognizer_release(void *handle);
```

Ownership is the whole contract: every returned `char *` is freed with `atc_parser_free`;
every handle is released with `atc_recognizer_release` and never used again. A NULL handle
returns NULL rather than trapping, so a caller that ignored a failed create fails at its own
mistake rather than inside the library.

**Unity (C#)** — `Recognizer : IDisposable`:

```csharp
using (var recognizer = Recognizer.Create(payloadJson))
{
    foreach (var issue in recognizer.Diagnostics().issues) Debug.LogWarning(issue);

    var result = recognizer.Recognize("air india 123 climb to flight level 260");
    foreach (var reply in result.readbacks) Speak(reply.spoken);
    foreach (var command in result.commands)
        if (command.isActionable) Apply(command);
}
```

There is a finalizer, but it is a backstop rather than the plan — it runs on the GC thread at
an unpredictable time, and until it does the decoded payload stays resident.

**React Native (TypeScript)** — `Recognizer`:

```ts
const recognizer = await Recognizer.create(payloadJson);
const result = await recognizer.recognize('air india 123 climb to flight level 260');
recognizer.dispose();
```

The RN handle is an **`Int`, not a pointer**. The bridge can only carry JSON-compatible
values, and handing JavaScript a raw address would let a stale number become a wild pointer.
An integer into a table the native module owns means a stale handle is a clean, reported error
(`atc_invalid_handle`) instead of a crash.

### A wire format shaped by its tightest consumer

New in `Sources/ATCParserKit/Wire/RecognitionWire.swift`. The domain types stay non-`Codable`
on purpose — they carry sum types with payloads, a `Range<Int>`, and a segmented phrase tree,
all natural in Swift and none of them expressible in C# or TypeScript.

Unity's `JsonUtility` sets the shape, being the tightest constraint: no dictionaries, no
polymorphism, **no nullable primitives**. So:

- flat objects; a sum type becomes a `kind` string plus its fields
- **no nulls, ever** — an absent string is `""`, an absent number is `0` beside a `has…` flag
- arrays only inside an object, never at the top level

TypeScript gets the benefit too: the recognition types have almost no optional fields, so
there is no optional-chaining on every access.

Three things are precomputed on the Swift side rather than left to each wrapper:

- **`readbacks`** — already grouped, one utterance per aircraft. Grouping by callsign and
  composing one reply is phraseology, not presentation; reimplementing it in TypeScript and
  again in C# is precisely the duplicated logic this package exists to prevent.
- **`isActionable`** — so the one check that matters cannot be got wrong, while `outcome`
  keeps all three values visible.
- **`intValue` / `hasIntValue`** — so a caller never re-parses a number across a bridge.

### Diagnostics cross the boundary

`atc_recognizer_diagnostics` / `recognizer.Diagnostics()` / `recognizer.diagnostics()` return
the payload problems found at decode time, plus the template counts.

This matters more on a bridge than in Swift. A broken template does not raise anything — it
simply never matches, so the instruction quietly does nothing. Without this, a Unity or React
Native developer has no way to see it at all.

A failed create reports **why**, in a JSON envelope (`decode_failed` vs `null_input`), rather
than collapsing to NULL. "Your payload is malformed" and "you passed a null pointer" need
different fixes.

### Tests

**170**, up from 151. The nineteen new ones drive the C ABI exactly as Unity does and pin the
wire format:

- a handle recognises, then releases
- one handle serves many transcripts — the point of not making it single-use
- two live handles are independent, and releasing one does not disturb the other
- a NULL handle returns NULL instead of trapping
- a bad payload reports its reason, and a null payload is distinguished from a malformed one
- the error envelope is valid JSON even when the decoder's own message contains quotes
- **no `null` is emitted for any input** — including no callsign, an unfilled slot, and
  nonsense in, because that is a constraint C# cannot defend itself against
- every key is present even when nothing matched, so a consumer never distinguishes
  "absent" from "empty"
- `outcome` is one of exactly three known strings, and `isActionable` always agrees with it
- an integer slot's `value` and `intValue` agree; a non-integer slot says it has no number
- readbacks arrive grouped one-per-aircraft, and a `Later:` branch reaches the wire
- output is byte-identical across runs, so a consumer can snapshot-test its integration

The C boundary is the only place in this package with manual memory management, and a real
Unity iOS build is a slow manual step — a retain/release mistake found in a game engine is
found in the worst possible place. CI now also checks all six exported symbols in **both**
xcframework slices, not two symbols in one.

## What is still not included

- **Android, desktop, WebGL.** The wrappers bridge a compiled Swift binary, so they remain
  iOS-only. Supporting Android would mean a second implementation of the parser, which
  defeats having one source of truth.
- **A stable JSON schema document** for the template wire format. The Swift file is the
  contract today, and the tests pin its shape; a published schema would be better.

## Upgrading

**From 1.2.0:** nothing to do; additive. To use the recognizer from RN or Unity, update the
package and follow the platform README.

**From 1.1.x:** also nothing to do — `parse` / `Parser.Parse` are unchanged.

Two things worth getting right at every call site, in every language:

1. **Act only on `isActionable`.** A `disabled` command was understood and gets a reply, but
   the deployment does not permit it — executing it is the bug this three-way outcome exists
   to prevent.
2. **Dispose the recognizer.** `using` in C#, `dispose()` on unmount in React Native. It holds
   a decoded payload.
